Conclusion

## Incomplete matrix

Thirteen M4 runs finished; three planned cells were NOT run. The spend ledger stopped the matrix at 90% of the $8 cap ($7.64 spent): Astra 6 on werkzeug-apply-conditions, Astra 6 on mypy-deferred-alias-crash, and the Opus + Sonnet team on mypy-deferred-alias-crash. Astra has no M4 result at all, so nothing here says whether Astra's M3 results (all killed at the cap with passing work) would change under the fresh-token cap. Every cell is one run, so no outcome below is a measure of reliability. The M3 runs (400k total-token cap) and M4 runs (300k fresh-token cap) are labelled in every table; the "M3 against M4" table puts them side by side.

What changed after the cap fix. Only 1 of 13 M4 runs hit a cap: the Opus + Haiku swarm on werkzeug, at 302,000 fresh tokens (its work passes the check). In M3, 13 of 19 runs on these three tasks were killed. Total tokens in M4 ran far above the old 400,000 line (11 of 13 runs exceeded it; Haiku on werkzeug used 2.1 million, almost all cache reads), so the old cap would have killed most of these. With the fresh-token cap, a finished run now means the agent stopped on its own, and "passed" is a usable column.

What separates contestants now. On the debugging task (mypy) Haiku and Sonnet fail again, as in M3; Opus, Sol and the swarm pass. On the multi-file task (werkzeug) every finished run passes except Haiku, which fails the check again; Sonnet, Opus, Sol and the team pass, and the swarm's capped run has passing work. So the split is the same one M3 suggested, and now it is not hidden behind a cap: the cheapest model fails the two hard tasks, and Sonnet fails the one where the fix has to go into the root cause rather than where the traceback ends. The M3 reading of that failure (a patch in the wrong place) was not rechecked on these runs.

What still does not separate. Sol, Opus, the team and the swarm all pass the hard tasks they finished, so among the strong setups the table does not rank them by outcome. Cost and time vary, but with one run per cell a difference of tens of percent is not a finding. The data task (IRS donee matching) is solved by every setup that ran it, and in M4 only the team and the swarm ran it: both now finish and pass (they were not run in M3). That is no new information about the models; it shows only that team and swarm are not blocked by the cap on this task.

Solo, team and swarm (n = 1, a hint only). On werkzeug: Opus alone $1.28 and 278 s, team $1.28 and 237 s, swarm $1.00 and 209 s but killed at the fresh-token cap. On mypy: Opus $0.67 and 265 s, swarm $0.71 and 250 s, team not run; Sol alone, $0.16, was the cheapest strong pass. On the data task the team cost $0.79 and the swarm $0.92 (M3 solo runs of the same task cost $0.08 to $0.52). Team and swarm cost about the same as Opus alone or more, use more fresh tokens (swarm: 92,000 to 302,000; Opus: 53,000 to 102,000) and take about as long. Nothing here shows that parallel workers help on tasks of this size.

Task length. The slowest M4 run took 302 seconds (about 5 minutes; Sol on werkzeug); most took 2 to 4.5 minutes. These tasks still do not reach the owner's target of 10 to 30 minutes for a strong agent. Raising the cap did not make them longer; the agents simply finish in a few minutes.

What the data does not show. It does not rank the strong setups, does not show variance, says nothing about Astra under M4, and does not test tasks that take 10 to 30 minutes. Next steps, if more spend is approved: run the three missing cells, repeat the cells where a flip would change the story (Sonnet on mypy, Haiku on werkzeug), and find tasks where Opus needs more than 5 minutes.

Methodology and limits

  • The unit is model + CLI, not the model alone. “Opus 5.5 · Claude Code” and “Astra 6 · Codex” each bundle a model with that vendor’s own agent harness, prompts and tools. A difference here can come from either half and this design cannot separate them.
  • Small sample. 7 tasks, and 1 to 2 runs per cell (the n shown in each table). A pass rate of 1/1 or 2/2 says the run worked, not that the contestant is reliable. No significance tests were run and none would be meaningful at this size.
  • Settings held equal: reasoning effort medium for every contestant (read back from each run’s own session files), connectors and user settings off, a clean HOME per run, the same prompt text, one process at a time. Per-run caps on tokens, dollars and minutes are enforced by the runner; a run that hits one is killed and marked capped, and counts as not passed.
  • Cap profiles (the “Cap profile” column says which one each run used). m2 (pilot): 150,000 total tokens and 10 minutes (400,000 and 15 for the team and swarm), per-contestant dollar caps. m3: 400,000 total tokens (cache reads included), 20 minutes, dollar caps about 3× the pilot’s. m4: 300,000 fresh tokens (input + cache writes + output, cache reads not counted), no cap on total tokens, 20 minutes, and dollar caps at least 2× the dearest m3 run of the same contestant. Runs under different profiles are never pooled into one cell or one leaderboard, because a token cap on total tokens mostly measured cache reads.
  • Pass means the run finished without hitting a cap and the hidden check passed. The hidden check is the upstream test file or cases (or, for a data task, a known-answer file) copied in only after the run; each task’s own manifest says exactly what it checks and what it forgives. Capped runs whose work would have passed are flagged in the failures list.
  • Dollars are dollar-equivalents. Every run used the owner’s Claude and Codex subscription logins, so no cash was billed per token. The figure is the recorded tokens × the versioned public list prices (table dated 2026-10-09); it is not an invoice, and plan limits were the real cost.
  • Tokens are summed over every model call in the session files, sub-agents included. Total includes cache reads, which are most of the total for every contestant and are billed at a small fraction of fresh input; fresh is input + cache writes + output. Neither is comparable between Claude Code and Codex, because the two harnesses cache and count differently.
  • Wall time is measured outside the CLI, from launch to exit, so it includes start-up. Machines and network were shared with other work, so treat differences under about 2× as noise.
  • Comparison with the real fix counts changed source lines (added plus removed, test files left out) against the upstream pull request. It is a size check, not a quality judgment; no model judged anything.
  • Tasks are real merged pull requests (fixes after 2026-06-30) from public repositories under permissive licences, plus data tasks built from public-domain government files. Absence of AI authorship in the originals could be checked only from trailers, labels and bot accounts. Whether any model had seen the fixes cannot be ruled out.
  • Runs lost to a harness fault, runs made against an earlier version of a task, and the difficulty probes on tasks that were dropped are kept out of every table here and are listed in evidence/m2-pilot.md and evidence/m3-tasks.md.
